# Replay 및 학습 진단 실험 — 첫 묶음 프로토콜 (2026-11-04)

사용자가 [후보 목록](../../docs/experiment_candidates_20261104.md)에 따른 학습 시작을 승인했다.
이번 범위는 아래 **네 조건의 첫 묶음**이다. 후보 목록 전체를 일괄 실행하는 계획이 아니다.
PER, n-step, Double DQN, mask, 보상 변경 등은 이번 묶음에 포함하지 않는다.
이 문서는 설계 명세이며 구현·실행·완료 여부는 이후 코드, 로그, 독립 검증 기록으로 확인한다.

사용자의 후속 요청에 따라 새 네 조건은 모두 **CUDA / NVIDIA GeForce RTX 4060**에서 실행한다.
GPU worker는 동시에 **1개**만 실행한다. 기존 CPU B를 CUDA로 다시 학습하는 대조군은 이번에
추가하지 않는다. 따라서 장치가 다른 기존 B와 새 조건의 차이를 한 변수의 효과로 해석하지 않는다.

## 2. 첫 묶음의 네 조건과 비교 관계

| 조건 | 주요 변경 | 훈련 pool | Replay | step 10,000 이후 처리 | 직접 비교 |
|---|---|---:|---:|---|---|
| S_CUDA: 단일 지도 진단 | 단일 원 훈련 지도에서 학습 | B train[0] | 2,000 FIFO | pause·clear 없음 | 일반화 순위 제외, B_CPU는 관측 참조 |
| R_CUDA: 큰 buffer | CUDA에서 capacity 10,000 | 기존 16개 | 10,000 FIFO | pause·clear 없음 | B_CPU 대비 장치+용량 차이, 단일 원인 대조 아님 |
| P_CUDA: pause 대조 | CUDA에서 clear 효과 분리를 위한 공통 대조 | 기존 16개 | 2,000 FIFO | buffer 유지, optimizer 256스텝 pause | F_CUDA의 장치가 같은 직접 대조 |
| F_CUDA: pause+clear | 같은 CUDA pause에서 buffer 1회 clear 추가 | 기존 16개 | 2,000 FIFO | clear 1회, optimizer 256스텝 pause | P_CUDA, clear의 직접 대조 |

이하 S/R/P/F는 각각 위 CUDA 조건을 뜻한다. 조건 순서는 S→R→P→F이고, 각 조건의 seed도
0→1→2로 **GPU worker 1개씩** 실행한다. 새 학습끼리 GPU를 공유해 동시에 실행하지 않는다.
진행 중인 곡선을 보고 clear 시점, 지도, 학습률, 평가 기준을 유리하게 바꾸지 않는다.

S는 작은 한 문제 자체의 학습 가능성과 seed 안정성을 확인하는 **진단**이다.
S의 훈련 greedy 성공률 분모는 1, 나머지 조건의 훈련 greedy 분모는 16이다.
이 두 훈련 성공률을 같은 난이도 순위로 비교하지 않는다. S의 검증 분모는 그대로 8이다.
S가 높은 검증 점수를 얻어도 본 묶음의 일반화 조건 승자 선정에는 포함하지 않는다.

R은 CUDA에서 큰 FIFO를 사용하는 후보 조건이다. B_CPU와는 **장치와 용량이 함께 다르므로**
R_CUDA/B_CPU 차이를 용량 하나의 효과로 부르지 않는다. 경험의 나이·구성은 기록하되 큰 buffer가
항상 유익한 성공 경험을 더 잘 활용할 것이라고 미리 가정하지 않는다. R에 clear, 우선 샘플링,
성공 경험 보존을 동시에 추가하지 않는다.

P_CUDA/B_CPU는 **장치와 pause가 함께 다르고** optimizer 갱신 횟수도 다르다. pause 하나의
효과로 해석할 수 없다. **F_CUDA/P_CUDA만 장치·pause가 같은 clear의 직접 대조**다.
F_CUDA/B_CPU 차이 전체를 clear의 효과라고 설명하지 않는다. R_CUDA/P_CUDA 역시 capacity와
pause가 함께 달라 순수 용량 대조가 아니다.

CUDA의 buffer 2,000·pause 없음 기준군이 없다는 제한을 결과표에 남긴다. 추후 용량 또는 pause
각각의 효과를 분리하려면 별도의 CUDA 기준군이 필요하지만, 이번 240k 계획에 자동 추가하지 않는다.

## 3. Clear와 pause의 정확한 시점

### 공통 전반부와 개입

P/F는 step 10,000까지 같은 규칙으로 학습한다. **step 10,000의 전이 추가, 정상 optimizer 갱신,
해당 시점의 target 동기화가 먼저 완료**되어야 한다. 그다음 개입 전 상태를 기록하고 F만 1회
replay clear를 수행한다. P는 replay를 유지한다. trigger를 갱신 전에 처리해 step 10,000의 정상
optimizer 갱신까지 빠뜨리지 않는다.

clear는 buffer의 유효 count와 쓰기 위치만 초기화한다. 배열 전체를 0으로 덮어쓸 필요는 없지만,
새로 채워지기 전의 오래된 레코드는 절대로 샘플링되면 안 된다.
모델·target·Adam·환경 위치·episode·epsilon 시계를 reset하지 않는다.
replay sampler RNG도 초기 seed로 되돌리지 않고 이어 사용한다.

### 공통 pause 구간

- pause 구간: **10,001~10,256, 양끝 포함**.
- 양쪽 모두 256번의 환경 상호작용과 전이 저장은 계속하고 optimizer 갱신만 하지 않는다.
- P는 buffer가 가득 차 있어도 이 구간에서 학습하면 안 된다.
- epsilon은 실제 전역 training step에 따라 계속 감소한다.
- 기존 target 동기화와 평가 일정은 양쪽에서 그대로 유지한다.
- 4스텝마다 갱신하므로 다음 optimizer 갱신은 **10,260**이다.
- F에는 재개 시 최소 256개의 새 전이가 있으며, 샘플링 전 batch 32 이상인지 확인한다.

| 조건 | 정상 20k 갱신 수 | pause로 빠지는 갱신 | 예상 실제 optimizer 갱신 |
|---|---:|---:|---:|
| B_CPU(기존)·S_CUDA·R_CUDA | 4,985 | 0 | 4,985 |
| P_CUDA·F_CUDA | 4,985 | 64 | 4,921 |

공식만 기재하지 말고 실제 카운터로 검증한다. **같은 CUDA·같은 seed의 P/F는 step 10,000
개입 전 및 step 10,256 pause 종료 시 online/target 가중치 hash가 정확히 일치해야 한다.**
clear 자체로 모델·target·optimizer 상태가 바뀌면 안 된다. optimizer·환경·episode·RNG의 유지
상태도 기록한다. 의도적으로 달라지는 replay 내용과 변동하는 wall time/파일 경로는 공통 가중치
hash에 섞지 않는다. 저장 컨테이너의 부가정보 대신 텐서 내용에 대한 일관된 hash를 사용한다.

같은 CUDA P/F의 요구된 hash가 다르면 clear 효과로 해석하지 말고 검증 불완전으로 처리하여
원인을 확인한다. 장치·라이브러리·결정성 설정을 기록하고, 비결정 연산이나 임의 CPU fallback을
숨기지 않는다. CPU B와 CUDA 조건 사이에는 이 공통 전반부 동일성 요구를 적용하지 않는다.
pause 이후 서로 다른 샘플 pool 때문에 학습 경로가 달라지는 것은 실험 대상이다.

## 4. 예산·동시 실행·중단 조건

| 범위 | 제한 |
|---|---|
| 계획된 새 학습 | 4조건 × 3seed × 20k = **240,000 training steps**, 12회 seed 학습 |
| 추가 학습 복구 | 전체 묶음에서 **seed 1개를 최대 1회** 다시 학습, 최대 추가 20,000 steps |
| 실패 시도 포함 새 학습 상한 | **260,000 training steps** |
| seed별 soft wall limit | **240초** |
| seed별 자식 프로세스 hard timeout | **270초** |
| 전체 실행기 wall limit | **3,600초, 60분**: 준비·학습·평가·저장·복구·집계 포함 |
| GPU 실행 | **CUDA / RTX 4060**, 동시에 **1 worker**, seed 순차 실행 |
| CPU 보조 연산 | 각 worker PyTorch CPU thread **1개**, 환경·자료 준비에 사용 |

seed마다 독립 프로세스와 CPU/CUDA RNG를 사용한다. worker별 결과 디렉터리를 분리하고,
부모 실행기가 집계·예산을 관리한다. CUDA 학습 worker는 앞 작업의 종료를 확인한 후 다음 것을
시작한다. 복구·스케줄링 중 같은 seed 작업을 중복 제출하거나 GPU worker를 병렬 추가하지 않는다.

240k/260k는 새로운 **훈련 상호작용** 예산이다. 평가 rollout까지 합한 전체 환경 상호작용 수가
아니다. 평가 스텝은 별도 집계하며 평가·복원·저장 시간도 wall 예산에 포함한다. B의 학습 결과를
재사용하더라도 필요한 검토·평가 비용까지 0으로 간주하지 않는다.

다음 worker를 시작하기 전에 남은 스텝·시간·시도 횟수가 해당 작업의 상한을 감당할 수 있는지
확인한다. 예산이 부족하면 새 작업을 시작하지 않는다. 표를 완성하려고 한 seed만 학습량을 줄이거나
다른 seed로 바꾸지 않는다. 불완전·실패 결과를 보존하고, 이를 완료된 0% 성능으로 둔갑시키지 않는다.
일반화 조건 순위에 사용하려면 세 seed가 모두 완료되어야 한다.

일시적인 저장 오류는 기존의 제한된 저장 재시도를 사용할 수 있다. 추가 학습은 없지만 시간은
소비한다. 재학습 복구는 원래 실패 시도와 로그를 보존하고 같은 seed·설정으로 처음부터 재실행한다.
replay/RNG가 없는 checkpoint를 완전한 학습 resume로 부르지 않는다. 완료 seed 재사용은 출처·
코드 버전·파일 hash를 남긴다. 추가 1회 복구 예산을 쓴 뒤에는 자동으로 더 늘리지 않는다.

작은 모델과 단일 환경에서는 GPU가 CPU보다 빠르다는 보장이 없다. CPU↔GPU 자료 전송,
batch 1 행동 추론, 환경 CPU 연산과 저장 시간이 영향을 줄 수 있다. 다음 시간을 따로 기록한다.

- 학습 갱신 연산 시간: backward/optimizer 등을 포함하는 범위를 명시한다.
- 행동 선택의 추론 시간: batch 1의 호출 횟수와 측정 범위를 명시한다.
- 전체 wall time: 준비·환경·전송·평가·저장·프로세스 비용을 포함한다.

CUDA 비동기 실행을 고려하여 이벤트 또는 동기화가 포함된 측정 방식을 사용하고 그 방식·오버헤드를
기록한다. GPU 이름·PyTorch/CUDA/드라이버·메모리 사용량·환경 스텝·optimizer 갱신 횟수·단일 seed
시간·묶음 시간을 함께 남긴다. 과거 CPU 실행과 현재 GPU 실행의 관측 초 수만으로 장치의 속도
우위를 확정하지 않는다. 장치 비교만을 위한 별도 벤치마크는 이번 학습 조건에 자동 추가하지 않는다.

## 5. 로그와 평가

원본 episode return, 최근 20개 episode 이동평균, 훈련 성공률 곡선, 500스텝마다 greedy 검증,
마지막 checkpoint의 훈련 greedy 평가를 보존한다. 마지막 미완료 episode는 완전한 episode
return 평균에 섞지 않는다.

본 실험에 필요한 추가 기록:

- 실제 optimizer 갱신 수, pause에서 제외한 갱신 수, training/evaluation steps, 시도 횟수.
- 개입 예정·실제 step, pause 시작/종료, clear 횟수, buffer count와 쓰기 위치.
- buffer 내 목표 도달 전이 수·비율, 경험 나이 분포, 지도별 점유·커버리지와 그 정의.
- 실제 샘플의 목표 도달 전이 비율·나이: 저장되어 있는 것과 학습에 재사용된 것을 구분.
- P/F 개입 전·clear 직후·pause 종료 시 제어 상태 및 모델·target·Adam reset이 없다는 확인.
- CUDA P/F의 10,000·10,256 시점 가중치 hash 일치 여부 및 장치·결정성·시간 측정 방식.
- Git/config/data 식별자, source snapshot, worker 로그, 실패·복구 출처, checkpoint step.

여기서 **목표 도달 전이**는 실제 목표 도착, reward=+1, terminated인 한 transition이다.
성공 episode 전체를 구성하는 모든 transition과 혼동하지 않는다.

평가에서는 같은 100행동 제한, 실제 지도, greedy 정책을 사용한다. 지도별 성공·행동 수·충돌·실제
이동 경로·A* 길이를 기록한다. return, 충돌 감소, 훈련 지도 성공, 새 지도 성공을 서로 대체하지
않는다. 실패 순환·Q값 분석에는 훈련/개발 검증 자료만 사용하며 최종 테스트를 조회해 원인을 고르지 않는다.

## 6. 순위와 해석

주요 비교는 seed별 **마지막 checkpoint** 성능과 평균·표본 표준편차(ddof=1)다.
중간 최고 checkpoint는 곡선 해석에 보충할 수 있으나, 유리한 값으로 끝점 비교를 대체하지 않는다.

잠정 일반화 조건 선택 후보는 **R_CUDA·P_CUDA·F_CUDA만**이며, **S_CUDA는 별도 진단 행**이다.
**B_CPU는 관측 참조 행이며 CUDA 조건의 승자 선택에 넣지 않는다.**
기존 기준을 유지한다: 마지막 validation 성공률 평균이 높은 쪽 → seed 표준편차가 작은 쪽 →
성공 경로 효율이 높은 쪽. 완전 동률이면 앞선 기준 조건을 유지한다. 성공 경로 효율은 성공 사례에만
정의되므로, 일부 seed에 성공이 없으면 해당 평균에 포함된 seed 수를 밝힌다.

clear의 직접 해석은 F_CUDA/P_CUDA에서 한다. R_CUDA/B_CPU는 장치+용량,
P_CUDA/B_CPU는 장치+pause 차이이므로 단일 원인 효과로 설명하지 않는다. CUDA 후보 사이의
잠정 순위도 모든 쌍에서 한 변수 효과가 분리됐다는 의미는 아니다. 전역 선택이 F여도
F_CUDA/B_CPU 차이 전체를 clear의 효과로 설명하지 않는다.

같은 8개 검증 미로를 세 정책으로 평가한 것은 24개 평가 episode이지 서로 다른 미로 24개가 아니다.
이 개발 세트는 이미 설정 선택에 사용됐다. 이번 결과도 개발 검증하의 잠정 관찰이며 최종 일반화
증명이 아니다. 큰 seed 편차·결측·실패·표본 제한·복구 코드 차이를 검토와 게시물 설명에 남긴다.

## 7. 실행 전 검증과 핸드오프

최소 검증 항목:

1. S의 실제 훈련 지도가 B train[0]이며 검증 8개 hash는 불변, 검증/테스트의 훈련 유입 없음.
2. 새 네 조건의 실제 장치가 모두 CUDA/RTX 4060이며 GPU worker는 동시에 1개. CPU B와 CUDA 사이의 bit 동일성 요구 없음.
3. clear 뒤 예전 레코드가 샘플링되지 않고, batch 부족 시 학습하지 않으며 모델·target·Adam은 유지.
4. pause 경계와 실제 횟수: 10,000 정상 갱신, 10,001~10,256 중단, 10,260 재개, 양쪽 4,921회.
5. 같은 CUDA P/F의 같은 seed에서 10,000·10,256 시점 가중치 hash가 정확히 일치함.
6. 프로세스별 CPU/CUDA seed 격리·출력 디렉터리 분리·hard timeout·전체 추가 복구 횟수 제한.
7. 불완전 조건이 완료 조건 순위에 들어가지 않으며, S와 B_CPU가 CUDA 일반화 승자 선택에서 제외됨.

실험 담당은 승인된 본 프로토콜 안에서 실행·복구하며 seed마다 같은 사용자 확인을 반복하지 않는다.
결과 담당은 수치·갱신 횟수·비교 관계·복구 출처·주장 범위를 독립 검증한다. 통과한 수치와 그림만
Instagram 담당에게 넘긴다. 게시물 제작을 위해 조건을 바꾸거나, 다음 후보 묶음을 자동 실행하거나,
공개 업로드하지 않는다.

본 파일은 설계 문서다. 새 실행기·예산 강제·CUDA 전환·기법이 이미 구현되고 통과됐다고 주장하지 않는다.
