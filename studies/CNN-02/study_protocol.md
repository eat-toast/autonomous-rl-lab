# 4단계 DQN 개발 실험 (2026-11-04 승인)

사용자가 학습량 → 탐색 기간 → 학습률 → 모델 너비 순서의 실행을 승인했다.
State, reward-v1, 미로 크기/세트, seed 0/1/2, 검증 주기 500스텝은 고정한다.
환경은 기존 10×10, train 16 / validation 8 / test 16이며 최종 test는 사용하지 않는다.
각 조건은 새 초기화에서 20,000스텝씩 학습한다. 이어 학습하는 방식이 아니다.

1. A: 기존 2,000스텝 대비 20,000스텝. FC 64, lr .001, epsilon decay 1,600 유지.
2. B: A에서 epsilon decay만 16,000으로 변경.
3. C: A/B 중 선택한 조건에서 lr만 .0003으로 변경.
4. D: A/B/C 중 선택한 조건에서 FC 너비만 128로 변경.

선택 기준은 마지막 checkpoint의 validation 성공률 평균, 낮은 seed 표준편차,
성공 경로 효율 순이다. 완전 동률이면 기존 설정을 유지한다.
3단계는 A/B, 4단계는 선택된 이전 기준/C를 비교하므로 모든 단계가 직전 단계와의 비교는 아니다.
선택에 최종 test 또는 훈련 지표를 사용하지 않는다. 8개 개발 검증 미로의 결과이므로 선택은 잠정적이다.

총 12개 seed 실행, 최대 240,000 환경 스텝.
seed당 soft wall limit 180초, 자식 hard timeout 210초.
전체 실행기 예산 2,700초. 다음 조건에 충분한 예산이 없으면 멈추고 기록한다.
replay 2,000개, CPU 1 thread. 오류/실패/시간 제한 결과는 보존한다.

추가 로깅은 에피소드 return 원본, 최근 20개 이동평균, 훈련 성공률 곡선,
마지막 checkpoint의 훈련 미로 greedy 성공률이다. 추가 진단은 평가에만 사용하며 학습하지 않는다.
시간 제한과 총스텝 제한은 실행 관리 목적의 변경이다.

동일 환경 스텝이라도 optimizer 갱신 횟수는 train_every=4에 따라 정해지며,
모든 20k 조건에서 4,985회다 (64스텝부터 4스텝마다 갱신).
보상 곡선의 마지막 미완료 에피소드는 합산하지 않는다.
return 상승이 목표 도달을 의미하지 않을 수 있으므로 greedy 성공률과 함께 해석한다.

실행: `python studies/CNN-02/scripts/run_study.py`
결과: `studies/CNN-02/results/`, 개별 run은 `runs/`에 보존.

## 저장 오류 복구 기록

B의 seed 1은 16,000스텝 모델 저장 중 Windows 파일 접근 오류(WinError 5)로 실패했다.
원본 run과 로그/중간 checkpoint를 보존한다. 모델/JSON 파일 교체에 제한된 재시도를 추가하고,
성공한 seed 0/2는 새 run에 복사해 출처를 기록하며 seed 1만 동일 설정으로 처음부터 재실행한다.
재학습을 이어가는 resume는 아니다. 같은 모델/보상/미로/seed를 유지한다.
복구용 재실행 한 번에 최대 20,000스텝을 별도 허용한다. 계획된 240,000스텝 외에
실패 시도까지 포함한 학습량 상한은 260,000스텝이며 전체 wall limit 2,700초는 유지한다.
보존된 실패 protocol과 recovery_provenance.json에서 코드/복사 출처를 확인할 수 있다.
